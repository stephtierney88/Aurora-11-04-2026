## Fast Policy

1. Read current maps, roadmap, handoff, skeleton, and lane notes before broad search.
2. Use a normal prompt for bounded work and a Goal only for a durable, evidence-verifiable multi-turn objective.
3. Treat large context as addressable data; search, slice, parse, and preserve source IDs.
4. Delegate only independent work, favoring read-heavy exploration, research, tests, and critique.
5. Keep one writer for overlapping files and one controller for each browser, desktop, emulator, or game.
6. Give every child a bounded task packet and require a structured evidence-bearing return.
7. Distinguish requested, admitted, queued, delivered, completed, rejected, cancelled, expired, and uncertain.
8. Never replay an uncertain side effect without readback or a stable idempotency contract.
9. Bind every gate to the exact claim it proves.
10. Do not repeat an identical failed attempt when relevant state is unchanged.
11. Turn durable lessons into refinement candidates before editing persistent policy, memory, skills, agent roles, or maps.
12. Default refinement to session scope; broader scope requires durable evidence and explicit approval.
13. Reject one-off noise, unsupported hypotheses, transient output, and proxy-gaming behavior.
14. Preserve before/after state, version, evidence, expected outcome, verification, and rollback.
15. Keep auth, permissions, network, command allowlists, executable skills, and controller ownership operator-controlled.
16. Preserve raw logs/artifacts; compaction and handoffs are derived indexes.
17. Mark complete only when the named evidence satisfies the objective.
18. Update stale scaffolding when durable truth changes and authority permits.
19. Give every imported behavior one typed setting with a compatibility default, maturity, scope, GUI tier, command/CLI parity, apply timing, readback, and rollback.
20. Show each effective value's winning source and whether a change is action-, turn-, session-, project-, or personal-scoped.
21. Preview and atomically apply related settings with an expected version and structured receipt; individually sent commands are not an atomic batch.
22. Configure observation, model wake, action dispatch, approvals, and persistence independently, even when a transparent profile bundles them.
23. Reserve `interactive` or `Codex-like` for a real in-turn tool/result loop, not a later capture and later scheduled turn.
